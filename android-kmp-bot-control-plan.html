DC Bot Android/KMP kezelő alkalmazás terv

Frissítve: 2026-07-27. Cél: mobil alkalmazásból kezelni azt a Discord botot, amely ugyanazon a Discord szerveren van, mint a bejelentkezett felhasználó, úgy hogy a bot meglévő music, queue, playlist és utility funkciói biztonságosan elérhetők legyenek.

IgenLehetséges mobil appból kezelni a botot
KMPJavasolt, ha iOS is cél
API kellNe a mobil app beszéljen közvetlenül Discord/Lavalink felé
Guild metszetUser guildök ∩ bot guildök = kezelhető szerverek
Rövid döntés: érdemes KMP-s alkalmazásban gondolkodni, ha Android mellett később iOS-t is fejlesztenél. Az első verzió legyen Android-first Compose UI-val, de a domain modellek, API kliens, auth/session logika és állapotkezelés menjen a shared KMP modulba. A botot ne Discord slash command self-invocationnel kezeld, hanem egy saját backend API-n keresztül.
Fontos Discord-korlát: publikus OAuth2-vel nem tudod megbízhatóan lekérdezni, hogy a user Discord kliensében éppen melyik szerver van megnyitva. A biztonságos modell az, hogy a mobil app listázza azokat a szervereket, ahol a user is tag és a bot is bent van, majd a user kiválasztja az aktív szervert. Opcionálisan ellenőrizhető, hogy a user éppen melyik voice channelben van azon a guilden, ha a bot gateway/cache oldalon látja ezt.

Miért nem elég a meglévő command rendszer?

Jelenlegi bot működés

  • Discord text commandok: !play, !pause, !savePlaylist.
  • Slash adapterek: /play, /queue, /playlist ....
  • A commandok IDiscordMessage, IDiscordMember, guild/channel wrapper és localized Discord response köré épülnek.
  • Ez jó Discordon belüli használatra, de mobil API contractnak túl Discord-specifikus.

Mobilhoz kell egy API boundary

  • Az app HTTP/WebSocket API-t hívjon, ne DSharpPlus objektumokat.
  • A backend validálja a Discord usert és a guild jogosultságot.
  • Az API strukturált DTO-kat adjon vissza: queue itemek, current track, playlist listák, error code-ok.
  • A meglévő service-ek elé érdemes application facade réteget tenni.

Guild kezelés: honnan tudjuk, melyik szerveren kezelhet a user?

LépésForrásMit ad?Döntés
1. User login Discord OAuth2 identify + guilds User ID, username/avatar, user guild list basic adatokkal. A mobil app saját sessiont kap a backendtől.
2. Bot guild lista Bot runtime cache / Discord gateway / saját DB guild_data Mely szervereken van bent a bot. A backend kezeli, nem a mobil kliens.
3. Metszet userGuilds ∩ botGuilds Csak azok a szerverek, ahol user és bot is jelen van. Ez lesz a mobil guild picker listája.
4. Jogosultság User permissions bitset, bot-config DJ role, allowlist, admin flag Mit tehet a user: read-only, playback control, playlist edit, admin. Endpointonként ellenőrizni kell.
5. Aktív guild User választása az appban Az app contextje: activeGuildId. Minden command/API call ezzel fut.
6. Voice-state check Bot gateway/cache, ha elérhető User éppen melyik voice channelben van. Playback parancsoknál opcionális vagy kötelező guard.
Ne erre építs: ne próbáld a mobil appból a Discord kliens aktuálisan megnyitott szerverét olvasni. A publikus Discord OAuth2 guilds scope alap guild listát ad, nem live kliens UI state-et. A Discord RPC/voice jellegű scope-ok több esetben partner/jóváhagyás kötelesek, ezért erre nem érdemes MVP-t tervezni.

Szabály: core modul soha nem függhet feature modultól. A :shared app shell függhet feature moduloktól, mert ő rakja össze a root navigationt és az app-szintű kompozíciót.

Javasolt modularizációs sorrend

  1. :core:common létrehozása, Resource és közös primitive-ek áthelyezése.
  2. :core:ui létrehozása, theme és reusable Compose komponensek áthelyezése.
  3. :feature:guild kivágása első vertical slice-ként: UI, presentation, domain, data.
  4. :core:auth kialakítása, majd auth session expect/actual storage befejezése.
  5. :feature:login kivágása, de az auth session infrastruktúra maradjon :core:auth alatt.
  6. :core:network stabilizálása, ApiService vagy endpoint kliensek végleges határainak kijelölése.
  7. Vékony feature-ek kivágása: :feature:profile, :feature:playlists, :feature:musiccontrol, :feature:settings.

Activity, Fragment vagy Compose Navigation?

Android-only Compose

Ajánlott

  • Egy MainActivity.
  • Nincs klasszikus Fragment, ha nincs meglévő XML/navigation örökség.
  • Compose Navigation: Auth, GuildPicker, Dashboard, Queue, Playlists, Settings.

KMP + Compose Multiplatform

Ajánlott, ha iOS UI is shared

  • Androidon egy Activity hostolja a shared App() composable-t.
  • iOS-en SwiftUI/UIViewController hostolja ugyanazt.
  • Navigáció shared szinten tartható.

Fragmentek

Csak ha kell

  • Legacy Android appba integrálásnál hasznos.
  • Új appnál felesleges réteg.
  • KMP/iOS út mellett nem ideális közös absztrakció.

Adatok, amiket egy usernek látnia kell

Guild dashboard

  • Bot online/offline és Lavalink connection state.
  • Aktív voice channel, ha van.
  • Queue count, playlist count, current repeat mode.
  • User jogosultság az adott guildben.

Playback és queue

  • Current track: cím, author, duration, elapsed position.
  • Queue lista: order, title, author, duration, requestedBy ha később tárolod.
  • Repeat track/list állapot.
  • Utolsó command eredménye/error code.

Playlist

  • Playlist nevek, track count.
  • Playlist trackek order numberrel.
  • Limit állapot: max playlist/guild, max track/playlist, max import.
  • Invalid/missing/corrupt track jelzés userbarát módon.

Biztonsági checklista

Backend

  • OAuth state és PKCE használata.
  • Access tokeneket backend oldalon titkosítva tárolni vagy rövid session tokenre cserélni.
  • Minden guild endpointon újra ellenőrizni: user is member, bot is member, permission elég.
  • Command rate limit user+guild alapon.
  • Playlist delete/queue clear confirm kötelező.
  • Audit log playback/queue/playlist write műveletekre.

Mobil

  • Secure storage: Android Keystore, iOS Keychain.
  • Ne tárolj Discord bot tokent mobilon.
  • Logout törölje a lokális sessiont.
  • Offline cache csak read-only adat legyen.
  • Permission denied állapot legyen egyértelmű.
  • Confirm UI veszélyes műveleteknél.
